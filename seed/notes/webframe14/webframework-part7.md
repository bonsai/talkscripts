# Webフレームワーク入門 第7回：LLMに渡すデータ形式——JSONLはいつ使う？ 使わないのは？

「DBのデータをどうやってLLMに渡すか」は、AI機能を作るときに必ずぶつかる疑問です。よく聞かれるのが「**JSONLで渡すべきですか？**」という質問。結論から言うと、**用途次第**で、リアルタイムの対話ではJSONLを使う必要はありません。今回は、データ形式の選び方を整理します。

まず **JSONL**（JSON Lines）は、1行に1件のJSONを並べた形式です。大量データをストリーム的に読み書きでき、機械処理に強いため、次のような場面で標準的に使われます。

1つ目は**RAGの取り込み（インデックス化）**です。ドキュメントを適切な長さにチャンク分割し、`{id, text, メタデータ}` を1行1件のJSONLで保存 → embedding生成 → ベクトルDBへ投入、という流れです。取り込みデータは「いつ誰が使うか」に関係なく一度だけ処理するものなので、JSONLが最適です。2つ目は**ファインチューニング**です。学習データはOpenAIをはじめ各社がmessages形式のJSONLを標準にしており、1行=1会話の完成した「対話教材」を用意します。3つ目は**バッチAPI**です。大量の非同期リクエストを1ファイルにまとめて送る際、JSONLを利用します。

一方、**リアルタイムのSNS機能でJSONLは不要**です。その場のAPI呼び出しでは、`messages` 配列というJSONに会話履歴を積んで送るのが標準で、いったんJSONLに変換する手間は無意味です。また、DBから取得したレコードを渡す際も、全行をそのまま詰め込むのではなく、**絞り込み、不要列を落とし、シンプルなJSONやMarkdownの表に整形**してから渡すのが安定します。LLMは文字列の整理された情報を好み、冗長な形式だとトークンが無駄になり精度も落ちます。

まとめると、**「取り込み・学習・バッチ」はJSONL、** **「対話・API呼び出し」はJSON（messages配列）**という使い分けです。そしてどちらでも前提になるのは、前回解説したコンテキスト管理——データを渡す前に量を減らし、必要なものだけを読みやすい形で。この「形式の選択」は地味ですが、AI機能の品質とコストを左右する重要な設計ポイントなのです。
