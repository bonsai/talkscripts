# 意味で grep する — Jev semgrep を解剖する

`bonsai/jev-semgrep` は「意味で探す」grep。TypeSafe AI の System One モデル **Jev** が1行ごとに yes/no の確率で判定してくれる。

## 1. 何を変えたのか

`grep` は文字列という**記号の一致**を見る道具だが、このツールは**意味の一致**を見る。`grep "angry"` は "angry" という語を探すが、`semgrep -e "customer is angry or frustrated"` は「怒っているお客さんに関わる行」を探す。入力された語が一字も出てこなくても、日本語の行でも拾ってくる。

この発想転換の土台にあるのが Jev というモデルの設計思想だ。Jev は「テキストを生成する LLM」ではなく、「**型付きの質問に確率で答えるモデル**」(System One)。`{"type": "noul", "instructions": "Does line L014 match: customer is angry?"}` という質問を送ると、`noul: 0.97` のように yes/no の確率が返る。

grep の核心が「行 × 正規表現」の比較だったのに対し、これは「行 × 命題」の比較だ。正規表現は字面を、Jev は**事実性 (proposition)** を判定する。

## 2. クロスエンコーダという決定的な違い

ベクトル検索は各ラインの埋め込みを**クエリを見る前に固定**する。だから測れるのは「トピック的な近さ」だけ。一方 Jev は行と質問を**一緒に読む**(クロスエンコーダ)。

`contrast.txt` の6行は全部「返金」を話題にしている。ところが「顧客が返金を要求しているか」という命題に答えさせると:

- 「返金してほしい。商品が壊れていた」→ 0.98
- 「返金処理が完了しましたのでご確認ください」→ 0.10
- 「The manager denied the refund request」→ 0.17

トピックは同じ、**主語〜述語の構造が違う**。誰が・したか・否定されているか、という述語論理の中身まで判定に入る。これが grep と grep の差ではなく、記号検索と意味判定の本質的な差だ。

## 3. 否定が「普通のブール演算」になる嬉しさ

確率は校正 (calibrated) されているので、閾値 0.5 一つで「X である」「X でない」を両方裁ける。すると **NOT は集合から引くトリックではなく、素直なブール演算**になる。

- `-e "about a refund" -v "customer is asking"` → 完了・ポリシー・拒否・処理期間の行が残る
- `-e "someone is angry" -a "the customer, not the staff, is the one acting"` → 担当者が怒って切った行 (0.05) が落ちる

行と行のコサイン類似度がほぼ同一でも、命題の主語を入れ替えれば確率がひっくり返る。**コサインには主語という自由度がそもそも存在しない**が、命題なら「主語を指定する」という形で平易に表現できる。この表現力が "across languages" と並ぶもう一つの目玉だ。

## 4. 言語をまたぐ検索 — 翻訳せずに概念を突き合わせる

日本語の意味クエリがフランス語・ロシア語・中国語・韓国語の返金要求行を全部 0.97 前後で拾う。翻訳ステップがない。これは「翻訳機能」ではなく**表現それ自体が概念の層で動いている**ことの帰結だ。

言語は表象の層であって、semgrep はその下の概念層で比較する。だから log やチケットが混言語でも、チームのメンバーがそれぞれの言語でクエリしても成立する。(悲しい注意書きもある: 英語が最も正確で、日本語は閾値付近で揺れる。境界線の判断は英語で書くのが安全。)

## 5. エンジニアリングとしての美学

このツールの美しさは、モデルの特性と実装が**一致**している点だ。

- **生成しなくて済む**から、1行ごとに命題を焼ける。1リクエストに30行を束ね、8本並列 → 210行が1秒未満。
- 質問は state (chunk の行群) とセットで送るので、バッチにしても確率は単発と変わらない(1行ずつ7秒かかるのが30行束ねて0.2秒)。
- AND/OR/NOT の各意味が**独立した確率**を返すから、評価は純粋なブール式で済む。`!(p[0] >= tPos) || ...` のような数行の `some` / `every`。
- grep と同じ exit code (0/1/2)、stdin 対応、`-v` 単独なら grep -v 互換、色付けまで grep の配色を踏襲。「道具」としての完成度が、概念的に新しいモデルの上に正規表現の文化を載せている。

`-r` で再帰するときは `.env*` や `*.pem` を自動で飛ばす。**検索した行は全部外部 API に上がる**から、これは単なる丁寧さではなく設計上の誠実さでもある。プライスは $0.042/M input tokens、レートリミット 1200 req/min で約 3.6 万行/分 — 実用の桁に入っている。

## 6. 結論: ツールというより世界観

これは "LLM で grep を作った" デモではなく、「**grep の目的は何だったか**」を問い直した作品だ。grep の目的は決して記号の探索ではなく、行への問いかけだった。今日まで grep が正規表現に縛られていたのは、それが**手元で無料で確実に評価できる唯一の機械**だったからに過ぎない。

Jev が「手軽に叩ける確率付きの述語評価機」として現れたとき、grep の魂は解放される。言語の壁も、字面の揺れも、否定構造も、全部「命題が成立するか」に収斂する。なにより**爆速で安い**。これが本当の意味での "grep by meaning" — ワイルドカードが正規表現に進化したように、正規表現が命題に進化した一歩だ。

唯一の欠点は「毎クエリで全文を再走査する」こと(固定の大規模コーパスに対する反復クエリはベクトル索引の方が有利)。しかし動く対象が「目の前のファイル」である以上、索引を張らないことでセットアップコストゼロを維持する選択は一貫している。
