LLM は賢い。だが賢いことと、ソフトウェアの中で信頼できることは別物だ。長く話せることは、しばしば長く迷い、長く嘘をつくことでもある。Jev の登場が刺さるのは、モデルが「もっと賢くなった」からではない。**LLM が抱えていた冗長さと不確実性を、数字に落とし込む別の原語を持ち込んだ**からである。

---

## 1. LLM の二つの病

生成モデルには、構造的に避けがたい二つの病がある。

ひとつは **冗長さ (verbosity / overgeneration)** だ。問いは「はい／いいえ」でも、答えは段落になる。分類したいだけなのに、理由・前置き・謝罪・言い換えがついてくる。パイプラインの途中で「このメールは請求か技術か」と聞きたいだけなのに、毎回散文を吐き出しては JSON にパースし、パース失敗をリトライし、スキーマ外のキーに泣き、レイテンシとトークンを溶かす。知能のコストの大半が、**判断そのものではなく、判断の包装紙**に消える。

もうひとつは **不確実性の不可視化** だ。LLM は自信満々に誤る。温度を下げても、logit を覗いても、「この答えがどのくらい当てになるか」を運用可能な形で取り出せないことが多い。人間は文面の勢いを確信度と取り違え、システムは成功レスポンスを正しさと取り違える。不確実性はあるのに、**数字として下流に渡せない**。だからゲートも、フォールバックも、人間エスカレーションも、勘で設計することになる。

冗長さはコストと複雑性を増やし、不可視の不確実性は事故を増やす。チャットには許されても、エージェントの内側・ルーティング・検疫・課金・権限の分岐には毒である。

---

## 2. Jev がやったこと：出力空間を潰す

Jev（TypeSafe の System One）は、テキストを生成しない。state と型付きの問いを受け取り、**Choice / Score / Noul** といった閉じた答えだけを返す。確率と confidence が付き、1 リクエストで複数の問いを並列に評価できる。公称は数十〜数百ミリ秒、入力は極端に安く、出力は実質無料に近い。

ここが本質だ。LLM が「書いてから解釈する」のに対し、Jev は最初から **答えの空間を数学的に小さくしている**。小さい空間では、スキーマ外の幻覚は起きようがない。冗長さは設計上消え、残るのは「どの選択肢か」「どのくらいか」「はいの確率はいくらか」という数字である。

言い換えれば、Jev は知能を会話から引き剥がし、**述語評価機**にした。行 × 正規表現だった grep が、行 × 命題になる。チケット × 部門、ログ × 要対応、イベント × 購買意欲——ソフトウェアが昔から欲しがっていた「if」の右側を、自然言語のまま、しかも確率付きで書けるようになった。

名前の由来も皮肉で正確だ。Jevons のパラドックス——効率が上がると消費が増える。判断が安く速くなると、判断の回数が爆発する。発表直後にゲートウェイ・エージェント・クローンが群がったのは、新しいチャットボットが欲しかったからではない。**プログラムから呼べる決定の単価が崩れた**からである。

---

## 3. 冗長さを数字にする、とは何か

冗長さの除去は、単に「短く答える」ことではない。短文 LLM でも冗長さは残る。問題は長さではなく、**答えが構造を持たない**ことにある。

Jev は冗長さを、次のような数字へ変換する。

- **Choice**：有限個のラベルとその確率分布
- **Score**：ルーブリック上の離散スコア
- **Noul**：命題の成立確率（0–1）

「たぶん請求まわりだと思いますが、場合によっては…」は消える。代わりに `billing: 0.81` がある。下流は閾値で切れる。A/B できる。集計できる。キャッシュできる。同じ問いを一万イベントに当ててヒストグラムが描ける。生成の一回性が、**測定可能な判定**に変わる。

ここに、アナリティクスや意味 grep が乗る必然がある。生成は物語を増やすが、判定は地図を増やす。地図は重ねられる。物語は毎回書き直される。

---

## 4. 不確実性を数字にする、とは何か

不確実性を消すのではない。**見える化し、運用の変数にする**のだ。

校正（calibration）の約束はざっくりこうだ。モデルが 0.9 と言った判断は、母集団ではおおよそ 9 割当たってほしい。個別の一発保証ではない。だがパイプライン設計者には十分強い。confidence が高ければ自動実行、中間なら LLM やルールにフォールバック、低ければ人間——という分岐が、文学ではなく数値で書ける。

LLM の不確実性は、しばしば「それっぽさ」の中に溶ける。Jev の不確実性は、確率と confidence という二つの軸に射影される。完全ではない。公式自身が jaggedness（文字通りの読解、弱い算術、日付、間接質問、context rot、敵対入力など）を列挙している。だが欠陥が列挙可能であること自体が、生成モデルの「なんとなく不安」より工学的だ。不安は設計できない。分布は設計できる。

重要な注意がある。**型が正しいことと、意味が正しいことは別**だ。`department=billing` と綺麗な JSON で返しても、中身は technical かもしれない。schema validation を正しさと同一視してはいけない。Jev が潰すのは冗長さと「形の不確実性」であり、世界認識の誤りまでは消えない。数字に落としても、その数字が指す事実は、なお検証の対象である。

## 5. 歴史的位置：生成の世紀に現れた判定の原語

ChatGPT 以降の十年は、生成を万民のインターフェースにした。その成功の裏で、ソフトウェア内部は逆に苦しくなった。エージェントは話しすぎ、ツールはパースしすぎ、コストは前置きに消え、失敗は自信満々に見える。

Jev の登場は、その反転に見える。RLHF の系譜から出て、「チャット用 RLHF の対極」を標榜する判断モデル。カーネマンの System 1 を名乗り、速い直感を API にした。マークシートが記述式を殺したわけではないように、Jev も LLM を殺さない。記述式が必要な場所は残る。だが **採点・振り分け・ゲート・探索** まで全部記述式でやっていた時代は、冗長だった。

正規表現の発明が「検索とは何か」を更新したように、命題評価機の普及は「自動化とは何か」を更新する。自動化の本丸は文章生成ではなく、**安全に呼べる決定**だった、という再発見である。

## 6. トータルで見る構図

まとめると、役割分担はこうなる。

| | LLM | Jev |
|---|---|---|
| 得意 | 生成・要約・多段推論・曖昧な相談 | 分類・ルーティング・ゲート・意味マッチ |
| 出力 | 開いたテキスト | 閉じた型＋確率 |
| 冗長さ | 構造的に抱えやすい | 設計上ほぼ排除 |
| 不確実性 | 文面に溶ける | 数字として渡せる |
| リスク | 形も中身も壊れうる | 形は壊れにくい／中身はなお誤りうる |

トータルの命題は短い。**LLM の冗長さは出力空間が開いていることの税金であり、不確実性は校正されない自信の税金である。Jev はその両方を、閉じた答えと確率という数字に射影する。**

射影は圧縮だ。圧縮には情報損失がある。だから算術も、詩も、交渉も、まだ LLM の領分だ。しかしソフトウェアが一秒に千回欲しがるのは詩ではない。半分は「これか、あれか」であり、もう半分は「どのくらい確かそうか」である。そこに数字が来た。

歴史が繰り返すとすれば、次に起きるのは予測どおりだ。判断が安くなれば、判断は増える。増えた判断は、また新しい冗長さと新しい不確実性を生む——どの閾値で切るか、どの定式化で聞くか、どの confidence で人に渡すか。Jevons の名を冠したモデルが、そのパラドックスの入口に立っているのは、ほとんど出来すぎたくらい正確である。

冗長さを捨てよ。不確実性を隠せ。ではなく、**測れ。**  
Jev が示したのは、そのための単位だった。
