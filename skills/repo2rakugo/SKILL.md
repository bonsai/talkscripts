# repo2rakugo

## 目的

リポジトリを「説明する」のではなく、リポジトリの中にある人間臭い矛盾・執着・失敗・発明・命名・設計思想を拾い、落語の構造へ変換する。

対象はコードそのものだけではない。

- README
- Issue / PR
- seed
- ADR / docs
- workflow
- 命名
- ディレクトリ構造
- 技術選定
- 失敗の痕跡
- TODO
- Git履歴から読める変化
- リポジトリ同士の関係

## 基本方針

1. 最初にrepoを観察する。いきなり創作しない。
2. repoの「技術用語」より「変なところ」を探す。
3. 変なところを、江戸落語でいう「人間の欲」に翻訳する。
4. 技術概念は笑いの道具として使い、説明会にしない。
5. 現実のrepoにない事実を発明しない。
6. 外部情報を使った場合は出典を台本生成前の素材として整理する。
7. 最後に必ず「落ち」を設計する。
8. オチは技術説明の要約ではなく、前半の伏線が反転する一言を優先する。

## repo観察プロトコル

### 1. Repo identity

以下を最初に把握する。

- repo名
- README
- 目的
- 主な技術
- ディレクトリ構造
- 最近の変更
- Issue / PR
- seedや研究メモ

### 2. Rakugo seeds

次の観点から最大5個の「落語の種」を抽出する。

- 欲：何を楽にしたがっているか
- 執着：なぜそこまでこだわるのか
- 矛盾：設計思想と実装がどこで食い違うか
- 誤解：技術用語を人間がどう勘違いできるか
- 失敗：うまくいかなかった痕跡
- 命名：名前だけで笑いが生まれる箇所
- 反復：何度も同じことをしている箇所
- 逆転：最初は欠点に見えるものが最後に意味を持つ箇所

### 3. 江戸落語化

技術概念を、江戸の人物・道具・商売・長屋・旦那・職人などへ写像する。

例：

- repository → 長屋の帳面
- issue → ご隠居への相談
- pull request → 町内会への改修願い
- CI → 夜中に見回る番頭
- agent → 勝手に仕事を始める小僧
- dependency → となりの店から借りている道具
- API → お店の勝手口
- model → やたら物知りなご隠居
- hallucination → 知ったかぶり
- deployment → 世間に店を開く
- bug → 店主だけが知らない穴
- workflow → 毎朝同じ順番で動く職人

ただし比喩は固定しない。repo固有の構造を優先する。

## 台本構造

基本は以下。

1. まくら
2. repo固有の違和感
3. 技術概念の導入
4. 登場人物が勘違いする
5. 勘違いが拡大する
6. 技術的事実を回収する
7. 江戸的な生活へ反転する
8. 強い落ち

### 単独読み上げモード

デフォルトは一人語り。

- 語り手が人物を演じ分ける
- 「父」「娘」など固定配役にはしない
- 読み上げだけで人物関係が分かるようにする
- セリフの前に話者名を必須にしない
- 音声化しやすい短文を優先する

### 将来の複数話者化

内部では話者を明示できる構造を保つ。

必要なら最終出力時に、

語り
旦那
小僧
ご隠居

のような話者へ分離できること。

## SF落語化

単なる江戸落語ではなく、技術が日常に入り込んだ世界を基本とする。

江戸の生活感 × 現代テック × 少し先のSF

を混ぜる。

未来技術を説明するより、

「そんな技術を江戸っ子が使ったら何を勘違いするか」

を中心にする。

## オチ設計

弱いオチを避けるため、完成前に次を確認する。

- 冒頭に伏線があるか
- repo固有の要素が最後に戻ってくるか
- 技術用語だけで終わっていないか
- 「なるほど」で終わらず「そういうことか」で反転するか
- 最後の一文だけでも笑えるか

オチ候補を3つ作り、最も強い構造を採用する。

## 出力形式

デフォルトは800〜1200字程度。

タイトル：
repoの固有名詞または特徴を生かした、落語らしい短い題名。

本文：
単独読み上げ可能なSF落語。

末尾に内部メモとして以下を付けてもよい。

- 元repo
- 拾ったseed
- 使用した技術概念
- オチの構造

ただし公開用台本では内部メモを除外する。

## 禁止

- repoを読まずに一般論から作る
- READMEだけを読んでrepo全体を断定する
- 存在しないIssueや機能を作る
- 技術解説記事を落語風にしただけの文章にする
- オチを「つまりAIとは〜」で終える
- 無理にコードを掲載する
- 技術用語を過剰に増やす

## 完成条件

「このrepoだから、この噺になった」と言えること。

repoの固有名詞を別repoに置き換えても成立してしまう場合は、再調査してrepo固有のseedを追加する。
